# Phase 3 (planned, not implemented) — feeding the graph into another LLM

## The problem

Phase 2 gives every company a knowledge graph that grows without bound as research
accumulates. The original ask also included feeding this graph as input to another LLM (e.g.
"summarize this account" or "draft an outreach email using what we know"). Dumping the *entire*
graph into a prompt doesn't scale: it blows the context window as a company's graph grows, most
of it is irrelevant to any single question, and token cost grows unbounded with research
volume. This is the standard "GraphRAG" retrieval problem — the graph itself is fine; the
naive way of using it as LLM input is not.

## Proposed design

1. **Embed node and edge text at write time.** When `graph_pipeline.py` upserts a node/edge,
   also compute and store a vector embedding of its name + attrs (e.g. "Jane Doe, Person,
   title: CEO"). Store it alongside the row — Postgres already has `pgvector`, so this stays in
   the same database rather than introducing a separate vector store, consistent with the
   Phase 2 "one database" decision. Adds one column (`embedding vector(N)`) to `nodes` and
   `edges`, plus a migration and the `pgvector` extension.

2. **At query time**: given a question (e.g. "what do we know about their leadership?"),
   embed the question, vector-search the company's nodes/edges for the closest matches, then
   expand N hops (1–2) from those matches via the existing edge table using a recursive CTE —
   this is well within what plain Postgres handles at this scale (a few hundred companies,
   modest per-company graphs); no dedicated graph engine needed.

3. **Serialize the bounded subgraph, not the whole graph, into the prompt** — as compact
   triples ("Jane Doe —WORKS_AT→ Acme", "Acme —HAS_CATEGORY→ HVAC & IAQ"), not raw JSON. Token
   cost stays bounded regardless of how large the company's full graph has grown.

4. **Cache a per-company graph summary** (regenerated whenever the pipeline runs), for cheap
   "give me an overview of this company" prompts that don't need targeted retrieval — avoids
   an embedding search + traversal for the common case of "just summarize everything so far."

5. **Provider**: reuse the Groq client plumbing from Phase 2 (same key-rotation logic already
   built) for the actual generation call once a subgraph + question are assembled — this phase
   is about the *retrieval* layer, not a new LLM integration.

## What this would touch (if built)

- `alembic/versions/xxxx_add_embeddings.py` — `pgvector` extension + embedding columns.
- `app/embeddings.py` — pure function wrapping an embedding call (same key-rotation/fallback
  shape as `groq_extractor.py`; Groq doesn't currently serve embedding models, so this would
  likely call a separate embedding provider — decide when this phase is actually scoped).
- `app/graph_retrieval.py` — vector search + N-hop expansion + triple serialization, all pure
  functions, unit-testable with a small seeded graph and no real embedding calls in tests
  (mock the embedding vectors, same pattern as `FakeExtractor`).
- `routers/graph.py` gains something like `POST /api/companies/{id}/ask` — question in, bounded
  subgraph + LLM answer out.
- A cached `graph_summary` (text + timestamp) on the `companies` row, regenerated by the
  pipeline alongside the hash-guarded extraction step already there.

## Why this isn't built now

Explicitly out of scope per direct instruction — Phase 2 (storage + extraction) needed to exist
and be solid before designing what reads from it. This plan exists so the eventual
implementation has a concrete starting point rather than starting from a blank page, and so the
schema decisions in Phase 2 (e.g. keeping everything in Postgres) don't need to be revisited —
`pgvector` slots into the same database with no architectural detour.
